# Feature Specification: コードグラフ探索 (Code Graph Search)

**Feature Branch**: `002-code-graph-search`

**Created**: 2026-06-12

**Status**: Draft

**Input**: User description: "コードグラフ探索 (refmesh 記事のグラフ探索コンセプトの code-rag 適用)。インデックス時に tree-sitter でコード間の関係 (ファイル間 import、シンボル定義、シンボル参照/呼出し) を抽出し、SQLite の edges テーブルに永続化する。検索ヒットを起点に BFS (深さ制限付き) で関連チャンク・関連ファイルを辿れるようにする。具体的には: (1) find_references を現行の grep ベース近似 (Phase 1 からの宿題) からグラフ参照に昇格、(2) 新 MCP ツール related_code を追加 — シンボルまたはファイルを起点に import/定義/参照の近傍を深さ指定で展開して返す。search_code のランキングには手を入れない (eval recall@5 ≥ 0.92 ゲートは維持、edges は検索スコアに混ぜない)。watcher の差分インデックスでも edges を同期する。Intel Mac 制約 (onnxruntime==1.17.3 / numpy<2.0 ピン) には触れない — 純 Python + SQLite + 既存 tree-sitter のみで実装。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - シンボル参照の正確な追跡 (Priority: P1)

コーディングエージェント (Claude Code) がリポジトリ内のシンボル (関数・クラス) の使用箇所を尋ねたとき、テキスト一致の近似ではなく、コード構造の解析に基づいた参照一覧が返る。コメントや文字列リテラル内にたまたま同じ単語が現れる行は結果に混ざらず、定義箇所と参照箇所が区別されて返る。

**Why this priority**: 既存 `find_references` は単語境界 grep の近似で、Phase 1 から「完全な実装は後日」と明記された宿題。誤検出 (コメント・docstring・同名異シンボル) がエージェントの判断を誤らせる。検索基盤の信頼性に直結する本機能の中核。

**Independent Test**: 既知のシンボル (例: 評価対象リポジトリの `get_openapi`) に対して参照一覧を取得し、(a) 定義箇所が定義として識別される、(b) コメント/文字列内のみの出現が結果に含まれない、(c) 実際の呼出し箇所が含まれる、の 3 点を確認できる。

**Acceptance Scenarios**:

1. **Given** インデックス済みリポジトリ, **When** 関数名を指定して参照を要求, **Then** 各結果に「定義」か「参照」かの種別とファイル・行位置が付与されて返る
2. **Given** コメント内にのみ出現する単語, **When** その単語を参照要求, **Then** コメント内の出現は構造ベースの結果に含まれない
3. **Given** グラフに記録のないシンボル (インデックス対象外ファイル等), **When** 参照を要求, **Then** 従来のテキスト近似に自動フォールバックし、結果が近似である旨が明示される

---

### User Story 2 - 検索ヒットの近傍展開 (related_code) (Priority: P2)

エージェントが検索でファイルやシンボルを見つけた後、「このコードに関連する周辺 (取り込んでいるモジュール、取り込まれている先、定義・参照しているシンボル)」を 1 回の呼出しで束として取得できる。深さを指定して 1 ホップ (直接関係) から 2〜3 ホップ (間接関係) まで展開を制御できる。

**Why this priority**: ベクトル検索は「点」を返すが、その周辺を辿るのが苦手 — これが本機能の出発点の問題意識。US1 (正確な参照) が土台で、その上に成り立つ展開機能のため P2。

**Independent Test**: 既知ファイル (例: `routing.py`) を起点に深さ 1 で展開し、そのファイルが import するモジュールと、そのファイルを import するファイルの双方向が返ることを確認できる。

**Acceptance Scenarios**:

1. **Given** インデックス済みリポジトリ, **When** ファイルを起点に深さ 1 で展開, **Then** import 元・import 先・定義シンボルが関係種別付きで返る
2. **Given** 同条件, **When** 深さ 2 で展開, **Then** 1 ホップ目の結果からさらに辿った関係が深さ情報付きで返り、件数は上限内に収まる
3. **Given** 存在しないシンボル・ファイルを起点に指定, **When** 展開を要求, **Then** 空結果とエラー種別が返る (クラッシュしない)

---

### User Story 3 - グラフの自動鮮度維持 (Priority: P3)

開発者が監視対象リポジトリのファイルを編集・削除すると、チャンク同様にコード関係グラフも自動で差分更新される。手動の再インデックスなしに、次の参照要求・近傍展開が最新のコード構造を反映する。

**Why this priority**: グラフが古いと US1/US2 の結果が現実と食い違い、信頼を失う。ただし初回は全量インデックスで成立するため、増分同期は P3。

**Independent Test**: 監視中リポジトリのファイルに新しい import 文を追加 → 保存 → 当該ファイル起点の展開に新しい関係が現れることを確認できる。ファイル削除でその関係が消えることも確認できる。

**Acceptance Scenarios**:

1. **Given** 監視稼働中, **When** ファイルに import を追加して保存, **Then** 短時間内にそのファイル起点の展開へ新しい import 関係が反映される
2. **Given** 監視稼働中, **When** ファイルを削除, **Then** そのファイルを起点・終点とする関係がグラフから消える
3. **Given** 全量再インデックス実行, **When** 完了後にグラフを照会, **Then** 削除済みファイルへの孤立した関係が残っていない

---

### Edge Cases

- 循環 import (A→B→A): 深さ制限付き探索が無限ループせず、訪問済みを再訪しない
- 同名シンボルが複数ファイルで定義されている場合: すべての定義候補を返し、1 つに絞り込まない
- 動的 import・メタプログラミング・文字列経由の参照: 静的解析の対象外 (結果に含まれない) — フォールバックのテキスト近似で補完可能であること
- 解析非対応の言語・拡張子のファイル: グラフ抽出をスキップし、インデックス全体は失敗しない
- 深さに過大な値 (例: 100) を指定: 上限値に丸められ、応答サイズと時間が暴走しない
- グラフ未構築の旧データベースで参照要求: フォールバック動作し、エラーで落ちない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはインデックス時に、コード間の関係 — ファイル間の取り込み (import)、シンボルの定義、シンボルの参照/呼出し — を抽出し、検索インデックスと同じ保存先に永続化しなければならない
- **FR-002**: `find_references` は、グラフに記録された定義・参照を種別 (definition / reference) 付きで返さなければならない。グラフに該当シンボルが存在しない場合は従来のテキスト近似へフォールバックし、結果が近似である旨を明示しなければならない
- **FR-003**: 新ツール `related_code` は、シンボル名またはファイルパスを起点に、関係の近傍を指定深さまで展開して返さなければならない。各結果には関係種別・方向・深さ (ホップ数) を含む
- **FR-004**: 近傍展開には深さ上限と返却件数上限を設け、上限超過の指定は丸めなければならない (応答の暴走防止)
- **FR-005**: `search_code` の検索ランキングは本機能の前後で不変でなければならない。グラフ情報を検索スコアに混入してはならない
- **FR-006**: 監視 (watcher) による差分インデックスは、チャンク更新と同一トランザクション境界でグラフも同期しなければならない (追加・変更・削除・移動)
- **FR-007**: 全量再インデックスはそのリポジトリのグラフを作り直し、孤立した関係 (存在しないファイル・チャンクを指す edge) を残してはならない
- **FR-008**: グラフ由来の返却コンテンツも未信頼コンテンツとしてマークされなければならない (既存の `context_trust` 規約に従う)
- **FR-009**: グラフ未構築の既存データベースでも全ツールが動作しなければならない (自動構築または明示的フォールバック)
- **FR-010**: グラフ照会系ツールの呼出しも既存の観測ログ (JSONL) に記録されなければならない

### Key Entities

- **Edge (コード関係)**: 関係の 1 件。起点 (ファイルまたはシンボル)、終点、関係種別 (imports / defines / references)、ソース上の位置 (ファイル・行)、所属リポジトリを持つ
- **Symbol (シンボル)**: 関数・クラス等の名前付き定義。名前、定義ファイル、行範囲を持ち、既存チャンクと対応付け可能

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 検索品質ゲート維持 — eval 20 問で recall@5 ≥ 0.92 (現行 0.95 から劣化しない。グラフは検索スコア非介入のため理論上同値)
- **SC-002**: 既知シンボル 10 件のサンプルで、構造ベースの参照結果にコメント/文字列内のみの出現が 0 件 (現行 grep 近似では混入する)
- **SC-003**: 既知シンボル 10 件すべてで、定義箇所が「定義」種別として結果に含まれる
- **SC-004**: 深さ 2 までの近傍展開が、評価対象リポジトリ (約 600 チャンク規模) で 1 秒以内に返る
- **SC-005**: ファイル変更から監視の取り込み猶予時間 (約 1 秒) + 数秒以内に、グラフ照会へ変更が反映される
- **SC-006**: pytest 全テスト green を維持し、グラフ抽出・照会・同期の新規テストが追加されている

## Assumptions

- 関係抽出の対象言語は Python を第一級とする (評価対象リポジトリが Python のため)。その他の言語は既存のコード解析基盤が対応する範囲でのベストエフォートとし、非対応はグラフ抽出スキップ (チャンク検索は従来どおり)
- 参照解決は名前ベースの静的解析とする。完全な型解決・エイリアス追跡は対象外 (同名シンボルは複数候補として返す)
- 動的 import・リフレクション・文字列からのシンボル解決は静的解析の対象外
- 関係はリポジトリ内に閉じる。リポジトリ横断・外部ライブラリ内部への展開は v1 対象外 (外部 import は「外部」として終端記録のみ)
- 実行環境は既存の constitution 制約に従う: 追加のネイティブ依存・新規 ML モデルは導入しない。既存のコード解析基盤・保存層・監視機構の拡張のみで実現する
- 既存の MCP ツール署名 (search_code / grep_code / get_file_range / list_symbols / list_repos / stats) は変更しない。find_references は返却内容が豊かになるが呼出し署名は維持する
