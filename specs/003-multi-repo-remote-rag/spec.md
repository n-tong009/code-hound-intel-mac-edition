# Feature Specification: 複数 dev コンテナ共有・汎用マルチ repo RAG サーバ化

**Feature Branch**: `003-multi-repo-remote-rag`

**Created**: 2026-06-19

**Status**: Implemented (2026-07-02) — 全 28 タスク完了・end-to-end 稼働確認済

**Input**: User description: "余り物の Mac A を RAG 専用機にし、複数の dev コンテナ (Mac B 上、Mac C から VSCode Remote-SSH で作業) から共有する汎用マルチ repo 検索基盤にしたい。各コンテナは自分のプロジェクト repo だけを検索でき、検索対象コードはリモート作業機にあるので RAG サーバ側へ届けてインデックスする。検索時には最新コードが反映されてほしい。現状の fastapi 単一 repo (eval 評価台) 構成からの脱却。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 複数コンテナが自分の repo だけを検索 (Priority: P1)

複数の dev コンテナがそれぞれ別プロジェクトを抱えており、全コンテナが共通の RAG サーバ (単一の SSE エンドポイント) に接続する。各コンテナは設定で「自分のプロジェクト repo 名」を一度宣言しておけば、検索時に毎回 repo を指定しなくても自分のプロジェクトだけがヒットする。別プロジェクトのコードが混ざらない。

**Why this priority**: マルチ repo 共有基盤の中核。これが無いと「汎用 RAG サーバ」が成立しない。repo 取り違えは別プロジェクトのコードが回答に混入する最悪の事故であり、その遮断が価値の源泉。

**Independent Test**: 2 つの repo を登録し、片方の repo 名を宣言したクライアントから検索 → その repo のヒットのみ返る。repo 宣言も明示指定も無いクライアントからの検索 → 黙って既定 repo を返さず、利用可能な repo 一覧を添えたエラーで指定を促す。

**Acceptance Scenarios**:

1. **Given** 複数 repo がインデックス済みでクライアントが repo「A」を宣言、**When** repo 引数を省略して検索、**Then** repo A のヒットのみが返る
2. **Given** クライアントが検索時に repo 引数を明示指定、**When** 宣言値と異なる repo を指定、**Then** 明示指定が優先される
3. **Given** repo の宣言も明示指定も無い、**When** 検索を実行、**Then** 既定 repo へ暗黙フォールバックせず、利用可能な repo 一覧を添えたエラーを返す
4. **Given** 存在しない repo 名を指定、**When** 検索を実行、**Then** 利用可能な repo 一覧を添えたエラーを返す

---

### User Story 2 - リモート作業機のコードを RAG サーバに取り込んで検索 (Priority: P1)

検索対象のコードは作業機 (RAG サーバとは別マシン) にある。RAG サーバはインデックス時に自分のローカルファイルしか読めないため、作業機のコードをサーバ側へ届けた上でインデックスする。届ける処理は差分転送で、変更が無ければほぼ無負荷。

**Why this priority**: 検索対象が無ければ US1 は空振りする。リモートのコードをサーバに乗せる経路が、この基盤を「使える」ものにする前提。

**Independent Test**: 作業機のプロジェクトをサーバへ取り込み、インデックス実行 → クライアントの repo 一覧にそのプロジェクトが現れ、検索でヒットする。再度取り込んで変更ゼロなら、再インデックスで重い再計算が走らない (変更ファイルのみ処理)。

**Acceptance Scenarios**:

1. **Given** 作業機のプロジェクトが未取り込み、**When** 取り込み + インデックスを実行、**Then** repo 一覧に出現し検索でヒットする
2. **Given** 取り込み済みで一部ファイルのみ変更、**When** 差分インデックスを実行、**Then** 変更ファイルのみ再処理され、未変更ファイルは再計算されない
3. **Given** 取り込み済みでファイルが削除された、**When** 差分インデックスを実行、**Then** 削除ファイルのチャンクと関連情報が索引から消える

---

### User Story 3 - 検索時に最新コードが自動反映される (Priority: P2)

作業機で編集したコードが、次の検索時点で索引に反映されていてほしい。利用者が手動で同期を叩く必要はなく、検索アクセスを契機に取り込み + 差分インデックスが完了してから検索結果が返る。変更が無ければ待ち時間はほぼゼロ。

**Why this priority**: 鮮度保証。ただし US1/US2 が動けば「手動同期 + 検索」で価値は出るため、自動化は P2。厳密な鮮度 (編集が必ず反映) は利便性を大きく上げるが MVP 必須ではない。

**Independent Test**: 作業機でファイルを編集 → 直後に検索 → 編集内容が結果に反映される。編集せずに連続検索 → 2 回目以降は同期で待たされず即座に返る。

**Acceptance Scenarios**:

1. **Given** 作業機で対象ファイルを編集、**When** クライアントが検索を実行、**Then** 取り込み + 差分インデックス完了後に最新内容を反映した結果が返る
2. **Given** 前回検索から変更が無い、**When** 再度検索、**Then** 取り込みは変更ゼロを検知し再インデックスを行わず、検索が即座に返る

---

### User Story 4 - 評価専用構成からの脱却 (Priority: P3)

サーバは元々 1 つの評価用リポジトリ (fastapi) を抱えた品質計測台だった。これを実運用の汎用マルチ repo 機へ移行する。評価用リポジトリは通常運用の検索対象から外すが、品質を再計測したくなった時のために評価資産 (コーパス + 質問セット) 自体は保全する。

**Why this priority**: 移行の後始末。検索機能そのものには影響しないため P3。ただしプロジェクト原則 (品質ゲート) との整合を取る必要がある。

**Acceptance Scenarios**:

1. **Given** 評価用リポジトリが通常運用の検索対象に含まれている、**When** 構成を移行、**Then** 通常の検索・repo 一覧に評価用リポジトリは現れない
2. **Given** 移行後、**When** 品質を再計測したい、**Then** 評価資産は保全されており再計測が可能

---

### Edge Cases

- repo 宣言ヘッダが空文字・空白のみ → 未宣言と同じ扱い (エラーで指定を促す)
- 作業機が接続不能 (オフライン) のまま検索 → サーバ側の既存索引で検索は継続できる (同期は失敗扱いで、最新でない旨が分かる)
- 取り込み中にインデックス対象外ファイル (node_modules 等の大量生成物) が混入 → 索引除外ルールで弾く
- 同期処理が進行中に別の検索が来た → 二重実行で索引が壊れない (同一 repo の同期は直列化される)
- 取り込み元に巨大ファイル (生成物・ロックファイル) → サイズ上限で除外し索引を汚さない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 複数のリポジトリを同時に保持し、検索・参照系の全機能を repo 単位でスコープできる
- **FR-002**: System MUST クライアントが接続単位で宣言した repo 名を、検索時に repo が明示指定されなかった場合の対象として用いる
- **FR-003**: System MUST repo の解決順を「明示指定 > 接続単位の宣言 > エラー」とし、いずれでも解決できない場合は既定 repo へ暗黙フォールバックせず、利用可能な repo 一覧を添えたエラーを返す
- **FR-004**: System MUST 存在しない repo を指定された場合、利用可能な repo 一覧を添えたエラーを返す
- **FR-005**: System MUST RAG サーバと別マシンにあるコードを、サーバ側ローカルへ差分転送した上でインデックスできる
- **FR-006**: System MUST 差分インデックス (変更・削除されたファイルのみ再処理し、未変更ファイルは再計算しない、ワンショットで完了する) を提供する
- **FR-007**: System MUST 「取り込み → 差分インデックス完了 → 検索」の順で最新コードを反映した結果を返せる経路を提供する (手動同期 + 検索で達成可)。変更が無い場合は再インデックスを省略し検索を即時化する
- **FR-007a**: System SHOULD FR-007 の同期を自動起動し、利用者の手動同期なしに厳密鮮度を達成する。MVP 必須ではない (US3 = P2) ため SHOULD。手動同期 (FR-007) でフォールバック可。自動起動の契機は 2 実装を許容する: (a) **検索アクセス契機** = クライアント側 pre-tool-use フック (contracts 記載の当初設計)、(b) **ファイル編集契機** = 作業機側のファイル監視常駐 (`scripts/watch_and_sync.sh` = fswatch デバウンス → `sync_repo.sh`)。**実装採択は (b)**: 作業機を Dev Container で運用する構成 (Mac C → Remote-SSH → Mac B コンテナ) では、コンテナ内で走るクライアントフックが Mac 側の `sync_repo.sh`・ソースパスへ到達できないため (a) が成立しない。(b) は Claude/コンテナ非依存で launchd 常駐でき堅牢。両実装とも「編集が後続検索に反映」(SC-005) を満たす
- **FR-008**: System MUST 通常運用の検索対象から評価用リポジトリを除外しつつ、評価資産 (コーパス・質問セット・過去結果) を保全する
- **FR-009**: System MUST インデックス除外ルールを全 repo に適用する。除外の責務は段で分かれる: 転送段 (rsync) は**パス/パターン除外のみ** (`.git`/`node_modules`/生成物/`.gitignore`/`.env` 等のパターン、巨大ファイルはサイズ)、**秘密情報の内容ベース検知は索引段 (hygiene) が担う**。「二重で弾く」とは段の責務分担であり、転送段が内容を走査する意味ではない
- **FR-010**: System MUST 既存のローカル接続セキュリティ (ループバック bind 強制、検索結果の未信頼コンテンツ標識、ログはパスのみ) を維持する
- **FR-011**: System MUST 既存の検索ランキング (ベクトル + 全文 + 融合 + リランク + 多様性) の挙動を変えない (本機能は repo スコープと同期の追加であり、品質には非介入)
- **FR-012**: System MUST 同一 repo に対する同期/インデックスの並行実行で索引が破損しないこと (直列化)
- **FR-013**: System SHOULD リモート作業機からサーバへの接続を、ループバック bind 維持と両立する経路 (トンネル) で確立する手順を提供する
- **FR-014**: System MUST 取り込みスナップショット (サーバ側の平文複製) を所有者限定権限 (`0700` 相当) かつ git 管理外で保護する。秘密情報は索引に入らずともディスク上の複製には着地し得るため、ファイルシステム権限で閲覧を限定する (Principle III Local-First 整合)
- **FR-015**: System MUST 接続単位 repo 宣言の経路を確定し、第一経路 (SSE URL `?repo=`) が成立しない場合の縮退経路を持つ。暗黙 `default` への退避は禁止 (FR-003)。縮退は「repo 毎に分離した SSE エンドポイント (パスで repo を一意化)」または「接続後の明示宣言ツール」のいずれかとし、いずれも『毎回 repo 指定不要』(US1) を維持する

### Key Entities *(include if feature involves data)*

- **repo (リポジトリ)**: 検索対象の論理単位。名前・取り込み元の所在・サーバ側のローカル保管場所・対象言語・索引メタ (チャンク数、最終索引時刻) を持つ。複数併存し、検索は repo でスコープされる
- **repo 宣言 (接続ラベル)**: クライアント接続が「自分の既定 repo はどれか」を表明する情報。接続単位で固定され、検索ごとの明示指定が無い時の解決に使う
- **取り込みスナップショット**: 作業機のプロジェクトをサーバ側ローカルへ差分転送した複製。索引の入力源。変更検知の単位はファイル
- **評価資産**: 品質計測用のコーパス + 質問セット + 過去結果。通常運用 repo からは外れるが保全される

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 2 つ以上の repo が同居する状態で、repo を宣言したクライアントの検索結果に他 repo のコードが 1 件も混入しない (混入率 0%)
- **SC-002**: repo の宣言も明示指定も無い検索は、誤った repo の結果を返さず 100% エラー (指定を促す) で応答する
- **SC-003**: リモート作業機のプロジェクトを、利用者がサーバへ SSH 接続して手作業でファイルを置く必要なく、取り込み + インデックスできる
- **SC-004**: 変更が無い状態での連続検索で、2 回目以降の同期由来の追加待ち時間が無視できる (重い再計算が走らない)
- **SC-005**: 作業機で編集したファイルが、その後の検索結果に反映される (厳密鮮度の達成)
- **SC-006**: 移行後、通常の検索・repo 一覧に評価用リポジトリが現れず、かつ評価資産から品質を再計測できる
- **SC-007**: 本機能導入の前後で、同一 repo・同一クエリに対する検索ランキングが変化しない (品質非介入の確認)

## Assumptions

- RAG サーバ機 (Mac A) は常時稼働の専用機とする。省電力 (スリープ) 運用は本フィーチャーの範囲外
- 作業機 (Mac B) のコードは差分転送 (rsync 相当) でサーバへ届く。転送の向きは作業機 → サーバ機の片方向で、既存のトンネル方向と揃える
- 自動同期は作業機側で起動する。当初は検索アクセス起点 (クライアントのツール実行前フック) を想定したが、Dev Container 運用ではフックが Mac 側スクリプトに到達不能なため、**編集起点のファイル監視常駐 (`watch_and_sync.sh`, launchd) を採択** (FR-007a)。サーバは自動同期の有無に依らず、手動同期 + 検索でも動作する
- 本機能は検索ランキングに非介入のため、品質 (recall) は理論上不変。プロジェクト原則の品質ゲート (Principle I) は「評価資産を保全し、ランキングに触る変更時にのみ再計測する」運用へ読み替える。評価用リポジトリ (fastapi コーパス + qa.yaml + 過去結果) は物理削除せず温存し、通常運用の `repos` 一覧からのみ外す。Constitution の評価対象記述はこの移行に合わせて改定する
- リモート接続・フック・クライアント設定は作業機側の作業であり、本リポジトリでは手順書として提供する (サーバ側コードと設定が実装対象)
- Intel Mac ピン (`onnxruntime==1.17.3` / `numpy<2.0`) と既存のチャンク・検索構成は変更しない
- 初期の取り込み対象は 1 プロジェクト (Market_Brief) だが、設計は複数 repo を前提とする
- 取り込み元の正確なパス・接続ホスト名・サーバ側保管場所・repo 名・対象言語などの環境固有値は、計画/実装フェーズで確定する
